# OpenROAD-3D Evaluation Flows

This directory contains the 3D backend evaluation flows for:

- `lol` logic-on-logic (LoL) intergation with placements provided by ICCAD2022 and 2023 contest binaries.
- `mol-analytical` memory-on-logic (MoL) integration with placements provided by our proposed mol-analytical placement method.
- `mol-tiling` memory-on-logic (MoL) integration with placements provided by our proposed mol-tiling placement method.

All commands below should be run from `OpenROAD-3D/flow`.

## Docker

Build the Docker image from the repository root:

```bash
make image
make check-image
```

Start the evaluation container from [start_docker_eval.sh](./start_docker_eval.sh):

```bash
cd OpenROAD-3D
./start_docker_eval.sh
```

That script is the shared evaluation entry point for both LoL and MoL. It uses
`open3dbench:2.0`, mounts `OpenROAD-3D` and `Place-3D`, and exports
`PLACE_3D_ROOT=/workspace/Place-3D` inside the container. The image includes
the OpenROAD executable built from `OpenROAD-3D/openroad`.

The current final image does not include Yosys or KLayout. OpenROAD backend
runs from existing DEF/ODB inputs are self-contained, while RTL synthesis and
GDS export currently require pinned external tools. Do not treat a host-tool
mount as a reproducible release configuration; packaging those tools in the
image remains required.

## Layout

```text
OpenROAD-3D/
├── openroad/                              # complete OpenROAD source baseline
└── flow/
    ├── script_routing/                    # die-aware GRT, DRT, and HBT scripts
    ├── run_lol_iccad2022.sh              # run the OpenROAD + HotSpot LoL evaluation flow for ICCAD 2022 placers
    ├── run_lol_iccad2023.sh              # run the OpenROAD + HotSpot LoL evaluation flow for ICCAD 2023 placers
    ├── run_mol_analytical.sh              # run the full backend implementation + HotSpot flow for mol-analytical
    ├── run_mol_tiling.sh                  # run the full backend implementation + HotSpot flow for mol-tiling
    ├── export_mol_defs.sh  # copy DEFs generated by Place-3D into a separate evaluation-pack directory
    ├── evaluation_pack/                   # standard DEF inputs to reproduce the original paper results
    └── evaluation_pack_custom/            # optional custom DEF inputs exported from Place-3D
```

## Die-Aware Routing Extension

The repository uses official OpenROAD commit
`790a4a35df35f7f95a65335ca571cf8bf2981dd2` as its baseline and retains only
the audited die-aware GRT/DRT, Resizer, macro-placement, and floorplan
extensions plus the corresponding flow entrypoints. The normal Open3DBench
flow remains the default; enabling the extension does not require edits to the
original `global_route.tcl` or `detail_route.tcl` scripts. Exact revisions and
the retained source delta are recorded in
[`openroad/OPEN3D_SOURCE.md`](openroad/OPEN3D_SOURCE.md) and
[`OPENROAD_COMPATIBILITY_AUDIT.md`](OPENROAD_COMPATIBILITY_AUDIT.md).

All extension scripts live in `flow/script_routing/`. The two main entrypoints
are `global_route_die_by_die.tcl` and `detail_route_die_by_die.tcl`; their
pass, validation, guide, and HBT helpers are kept beside them.

The global router classifies nets by die, assigns a per-net routing-layer
range, and routes the bottom and top groups in isolated passes. Boundary-pin
access and guide-connectivity completion are performed in the router before
the pass guides are merged. The detailed router derives the same per-net layer
ranges from the merged guides and rejects maze expansion outside each net's
allowed range. Its bottom and top passes run in separate OpenROAD processes
to release routing memory between passes.

For HBT-enabled flows, cross-die nets are split around placed HBT terminals
before routing. The terminals remain ordinary pin targets through GRT and DRT.
After detailed routing, each terminal pair is merged back into one net and
replaced by a fixed hybrid-bond via, followed by a final DRC check.

```bash
cd OpenROAD-3D/flow
OPEN3D_DIE_BY_DIE=1 \
OPEN3D_HBT=1 \
./run_mol_analytical.sh
```

`OPEN3D_HBT=1` selects
`platforms/nangate45_3D/lef/NangateOpenCellLibrary.tech.open3d.lef`, which
contains the hybrid-bond via and 5 um pitch rules. HBT mode requires
`OPEN3D_DIE_BY_DIE=1` so its terminals remain routable through DRT. Leave both
switches at their default value of `0` to retain the original Open3DBench path.

## LoL Evaluation

`OpenROAD-3D` reads LoL DEFs directly from `Place-3D`. The LoL design configs use:

```text
Place-3D/binaries/converted_output/<variant>/<method>/*.def
```

where:

- `variant` is either `default` or `inflated`
- `method` is the selected placer name, such as `cadb1021`, `cadb1038`, or `tcad25`

If you use the pre-generated artifacts already included in `Place-3D`, you can run the evaluation directly without reproducing the LoL placement pipeline.

Typical commands:

```bash
cd OpenROAD-3D/flow
./run_lol_iccad2022.sh <default|inflated> <method>
./run_lol_iccad2023.sh <default|inflated> <method>
```

Example using the `tcad25` placer:

```bash
cd OpenROAD-3D/flow
./run_lol_iccad2023.sh default tcad25
```

If you want to reproduce the full LoL pipeline yourself, follow the steps in `Place-3D` first:

1. generate LoL inputs in `Place-3D`
2. run a LoL placer in `Place-3D/binaries/`
3. convert the placer outputs into DEFs in `Place-3D`
4. evaluate the resulting DEFs in `OpenROAD-3D`

### LoL Outputs

For LoL evaluation, final experiment logs are archived under:

- `logs/nangate45_3D/<design>/<method>_<variant>/`

Intermediate work directories are created under:

- `logs/nangate45_3D/<design>/lol/`
- `results/nangate45_3D/<design>/lol/`

The archived directories contain the runtime log and copied evaluation artifacts such as generated PNGs and HotSpot outputs when available.

## MoL Evaluation

There are two supported ways to provide DEFs for the MoL experiments.

### Option 1: Use the packaged evaluation DEFs

If you want to reproduce the results reported in our paper, first download `evaluation_pack.tar.gz` from [Google Drive](https://drive.google.com/file/d/19ypJmK_8yvWz7MN-qbyokmuoW0faEekm/view?usp=sharing) and extract it under `OpenROAD-3D/flow` as `evaluation_pack/`:

```bash
cd OpenROAD-3D/flow
wget -O evaluation_pack.tar.gz 'https://drive.google.com/uc?export=download&id=19ypJmK_8yvWz7MN-qbyokmuoW0faEekm'
tar -xzf evaluation_pack.tar.gz
```

The run scripts read DEFs from:

- `evaluation_pack/mol-analytical/*.def`
- `evaluation_pack/mol-tiling/*.def`

If you want to reproduce the results reported in our paper, you can run the flow directly without any extra step.

```bash
cd OpenROAD-3D/flow
./run_mol_analytical.sh
./run_mol_tiling.sh
```

Both scripts point to `evaluation_pack`.

### Option 2: Use DEFs generated by Place-3D

`Place-3D` can generate final DEFs under:

- `Place-3D/results/mol/mol-analytical/mol_final/<design>_suffixed.def`
- `Place-3D/results/mol/mol-tiling/mol_final/<design>_suffixed.def`

The OpenROAD mol scripts do not read those files directly. They read from a pack root on disk. By default that pack root is `evaluation_pack/`, but you can point them to a separate custom pack such as `evaluation_pack_custom/`.

If you are following this custom-DEF workflow, you do not need to download `evaluation_pack.tar.gz`.

To avoid overwriting the standard reproducibility inputs, the export script writes to `evaluation_pack_custom/` by default. Because of that, the recommended workflow is:

1. Follow the instructions in `Place-3D` to generate the custom MoL DEFs.
2. Export the generated DEFs into `OpenROAD-3D/flow/evaluation_pack_custom/<method>/`.
3. Run the OpenROAD evaluation flow with `evaluation_pack_custom` as the pack root.

Example:

```bash
cd OpenROAD-3D/flow
./export_mol_defs.sh mol-analytical
./run_mol_analytical.sh evaluation_pack_custom
```

```bash
cd OpenROAD-3D/flow
./export_mol_defs.sh mol-tiling
./run_mol_tiling.sh evaluation_pack_custom
```

### MoL Outputs

For MoL evaluation, final experiment logs are archived under:

- `logs/nangate45_3D/<design>/mol-analytical/`
- `logs/nangate45_3D/<design>/mol-tiling/`

Intermediate work directories are created under:

- `logs/nangate45_3D/<design>/mol/`
- `results/nangate45_3D/<design>/mol/`

The archived directories contain the runtime log and copied evaluation artifacts such as generated PNGs and HotSpot outputs when available.
